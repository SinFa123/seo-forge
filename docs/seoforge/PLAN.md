## 1. Verified upstream facts

These were read directly from upstream at the commit above.
Paths are relative to the repo root.

### Architecture

- Backend flow is TanStack server function to service to repository, per `CLAUDE.md` and `.greptile/rules.md`.
- Server functions live in `src/serverFunctions/<feature>.ts` and use `createServerFn`, `.middleware(requireProjectContext)` from `src/serverFunctions/middleware.ts`, and `.validator(<zod schema>)`.
  Example: `src/serverFunctions/keywords.ts`.
- Services live in `src/server/features/<feature>/services/`.
  The public service object is a plain `as const` object of functions.
  Example: `src/server/features/keywords/services/KeywordResearchService.ts` re-exporting from `services/research/*.ts`.
- Repositories live in `src/server/features/<feature>/repositories/` and import `db` from `@/db` and tables from `@/db/schema`.
  Example: `src/server/features/keywords/repositories/KeywordResearchRepository.ts`.
- Zod input schemas shared by the route, server function, and MCP live in `src/types/schemas/<feature>.ts`.
  Row types live in `src/types/<feature>.ts`.
  Example: `src/types/schemas/keywords.ts`, `src/types/keywords.ts`.
- Shared pure code used by both client and server lives in `src/shared/`.
- Market resolution (default location and language from the project) is `resolveMarket` in `src/shared/keyword-locations.ts`, used by both server functions and MCP tools.

### DataForSEO integration

- All DataForSEO calls go through `src/server/lib/dataforseo/`.
  Each API section has a file (`serp.ts`, `labs.ts`, `google-ads.ts`, `backlinks.ts`, `ai.ts`, `business.ts`, `lighthouse.ts`).
  Fetchers call `dataforseoPost` from `core.ts`, then `assertOk`, `parseTaskItems` with a Zod item schema, and `buildTaskBilling` from `envelope.ts`, returning `DataforseoApiResponse<T>` with `data` and `billing`.
  Reference: `fetchLiveSerp` in `src/server/lib/dataforseo/serp.ts`.
- Metering is `createDataforseoClient(customer)` in `src/server/lib/dataforseo/client.ts`.
  It is an object literal of sections, each entry `meter(customer, fetchX, defaultFeature?)`.
  `meter` and `meterDataforseoCall` are module-private.
  In non-hosted auth modes metering short-circuits and just returns `data`.
- Credit features are mapped from the API path in `src/shared/billing-credit-features.ts`.
  Paths under `serp/*` that are not Google maps or local finder map to `keyword_research`.
  YouTube SERP paths therefore already map to `keyword_research` with no edit.
- Upstream already wraps Google Ads search volume (`fetchAdsSearchVolume` in `google-ads.ts`, exposed as `client.keywords.adsSearchVolume`).
- Upstream has no Google Trends wrapper and no YouTube wrapper.
- Result caching uses R2 via `src/server/lib/r2-cache.ts`: `buildCacheKey(prefix, params)`, `getCached(key)`, `setCached(key, value, ttlSeconds)`, and callers validate cached values with Zod.
  Reference: `src/server/features/keywords/services/research/research.ts`.

### Database

- Schema files per dialect: `src/db/<name>.schema.ts` (SQLite via `drizzle-orm/sqlite-core`) and `src/db/pg/<name>.schema.ts` (Postgres via `drizzle-orm/pg-core`).
  Reference pair: `src/db/gsc.schema.ts` and `src/db/pg/gsc.schema.ts`.
  Timestamps are `text` columns.
  SQLite default is `sql\`(current_timestamp)\``; Postgres default is the `isoNow` expression defined at the top of each pg schema file.
- Barrels: `src/db/d1/schema.ts` and `src/db/pg/schema.ts` re-export every schema file.
  `src/db/schema.ts` is the provider-aware barrel that types everything as the SQLite schema and casts at runtime.
  `src/db/schema-parity.test.ts` asserts the two dialects are structurally identical.
- `db` from `src/db/index.ts` is the provider-aware handle typed as the D1 client.
  The Drizzle query builder accepts any table object, so a repository can import tables from a different barrel and still use `db`.
- Drizzle configs: `drizzle.config.ts` (sqlite, schema `./src/db/d1/schema.ts`, out `./drizzle`) and `drizzle-pg.config.ts` (postgresql, schema `./src/db/pg/schema.ts`, out `./drizzle-pg`).
- D1 migrations are applied by `wrangler d1 migrations apply DB --local|--remote` using `migrations_dir: "drizzle"` in `wrangler.jsonc`.
  Alchemy (`alchemy.run.ts`) applies the same directory with `migrationsTable: "d1_migrations"`.
  Docker self-host runs `pnpm run db:migrate:local` in `docker-entrypoint.sh`.
  Postgres migrations run through `drizzle-kit migrate --config drizzle-pg.config.ts`.
- Upstream is at migration `0044` in `drizzle/` and has 23 migrations in `drizzle-pg/`.
- `knip.jsonc` lists the drizzle configs and schema barrels as entries.
  New standalone config files must be added there or `pnpm ci:check` fails.

### MCP

- Tools live in `src/server/mcp/tools/<name>.ts` and export an object `{ name, config: { title, description, inputSchema, outputSchema, annotations }, handler }`.
  Project-scoped handlers are wrapped with `withMcpProjectAuth` from `src/server/mcp/project-auth.ts`.
  Reference: `src/server/mcp/tools/research-keywords.ts`.
- Shared input schemas: `projectIdSchema`, `locationCodeSchema`, `languageCodeSchema` in `src/server/mcp/schemas.ts`.
- Output helpers: `looseObjectOutputSchema` and `optionalMetaOutputSchema` in `src/server/mcp/output-schemas.ts`; `mcpResponse` in `formatters.ts`; `buildProjectMeta` in `context.ts`; `formatMcpTable` and `McpTableColumn` in `table.ts`.
  Every tool returns the full rows in `structuredContent` and a pipe table in the text block.
- Registration is in `src/server/mcp/server.ts`: import the tool and add one `register(<tool>)` line.
  `register` wraps `instrumentMcpToolHandler`, which is required by `.greptile/rules.md`.
- The MCP server identity is `name: "OpenSEO MCP"`, `title: "OpenSEO"` in `src/server/mcp/server.ts`.
- Test helpers: `makeToolContext` and `textContent` in `src/server/mcp/tools/tool-test-support.ts`.
- End-to-end MCP verification procedure: `.agents/skills/verify-local-mcp/SKILL.md`.

### Client

- Routes are file-based under `src/routes/_project/p/$projectId/<feature>.tsx`.
  `src/routeTree.gen.ts` is generated.
  A route validates search params with `validateSearch: <zod schema>` and renders a page component from `src/client/features/<feature>/page/`.
  Reference: `src/routes/_project/p/$projectId/keywords.tsx`.
- Client feature folders: `src/client/features/<feature>/{page,hooks,components,state}`.
  Reference: `src/client/features/keywords/`.
- Data fetching is TanStack Query calling the server function.
  Query keys include project scope and every input.
  Stale time for research is 24 hours (`KEYWORD_RESEARCH_STALE_TIME_MS` in `useKeywordResearchData.ts`).
- Tables use `AppDataTable`, `useAppTable`, `makeSelectionColumn`, `useSelectionAnchor` from `src/client/components/table/AppDataTable.tsx` with TanStack Table column helpers.
  Reference: `src/client/features/keywords/page/KeywordResearchDesktopTable.tsx`.
  Mobile has a separate results component (`KeywordResearchMobileResults.tsx`).
- Recent searches are the search tabs feature: `src/client/features/search-tabs/` with `SearchTabStrip`, `useSearchTabNavigation`, and a `SearchTabInput` union in `types.ts`.
- Sidebar navigation is the `projectNavItems` array in `src/client/navigation/items.ts`.
  Icons are from `lucide-react`.
- Shared UI primitives in `src/client/components/`: `LocationSelect`, `SegmentedToggle`, `Modal`, `PortalMenu`, `SafeExternalLink`, and `table/`.
- Brand strings are literal `"OpenSEO"` in about 50 files under `src/`, with no shared constant.

### Resolved on 2026-09-06 (latency)

- Single-call latency measured from the VPS: YouTube organic live SERP about 14 s, video info about 4 s, Google Trends explore about 7 s, Google Ads search volume about 0.2 s, YouTube suggest about 0.1 s.
  The SERP latency dominates every research run.

### DataForSEO YouTube endpoints (from DataForSEO docs)

- `POST /v3/serp/youtube/organic/live/advanced`.
  Params: `keyword`, `location_code` or `location_name`, `language_code` or `language_name`, `device`, `os`, `block_depth` (default 20, max 200).
  Item fields: `video_id`, `url`, `thumbnail_url`, `channel_id`, `channel_name`, `channel_url`, `channel_logo`, `title`, `description`, `highlighted`, `badges`, `publication_date`, `timestamp`, `duration_time`, `duration_time_seconds`, `views_count`, `is_live`, `is_shorts`, `is_movie`, `rank_group`, `rank_absolute`, `block_rank`, `block_name`.
  Live price about 0.002 USD per 20 results.
- `POST /v3/serp/youtube/video_info/live/advanced`.
  Params: `video_id`, `location_code`, `language_code`; desktop only.
  Returns views, likes, comments count, duration, publication date, timestamp, title, description, thumbnail, category, keywords, streaming and subtitle info, and channel name, id, url, logo, and subscriber count.
  Live price about 0.006 USD per request.
  Exact JSON key names must be confirmed from the docs sample response when writing the Zod schema.
- `POST /v3/keywords_data/google_trends/explore/live`.
  Accepts `type` with values `web`, `news`, `youtube`, `images`, `froogle`.
  `item_types` include `google_trends_graph` and `google_trends_queries_list`.
  Queries list returns top and rising related queries.
  Interest values are relative, 0 to 100, and 0 means not enough data.
  Up to five keywords per request.
- DataForSEO has no YouTube search volume, no YouTube autocomplete, and no channel listing endpoint.

## 5. Scoring model

All formulas live in `src/shared/youtube.ts` as pure functions with tests.
Constants are grouped in one exported `YOUTUBE_SCORING` object with an `ESTIMATOR_VERSION`.
Version 1 values below are starting points and are expected to change in Phase 6.

### Views per hour

`viewsPerHour = viewsCount / max(1, hoursSince(publicationTimestamp))`.
Label it "avg views/hr since publish" everywhere.

### Channel multiplier

`channelMultiplier = videoViews / median(views of the channel's last 20 uploads excluding this video)`.
Display as `Nx` with one decimal below 10 and none above.
Null when the Data API key is unset or the channel has fewer than 5 other uploads.

### Competition (0 to 100)

Two variants share one function with a flag for whether subscriber data is present.

Inputs from the top 20 SERP results:

- `log10` of median views.
- `log10` of median subscriber count (seed only).
- Share of results younger than 12 months.
- Share of results that are Shorts or live.
- Number of distinct channels (fewer distinct channels means one channel dominates, which is harder).

Each input is normalised to 0 to 1 against fixed bounds, weighted, and summed.
Version 1 weights: views 0.40, subscribers 0.25 (redistributed to views when absent), freshness 0.15, distinct channels 0.10, shorts share 0.10.

### Search volume estimate

Version 2 (calibrated 2026-09-06, see Phase 6 in section 9):

1. `anchor` is Google Ads monthly volume for the keyword.
2. `estimate = round(coefficient * anchor ^ exponent)` with `VOLUME_POWER_LAW = { coefficient: 4815, exponent: 0.303 }`, fitted by least squares on log-log VidIQ versus Google volume.
   VidIQ's volume grows far slower than Google's (about 100x Google at 1K Google searches, 1.2x above 100K), so a constant share cannot fit both ends; the power law gets 76% of the sample within one order of magnitude.
3. Google Trends (type youtube) is requested once for the seed alone.
   Its interest graph only decides the seed's confidence; its related queries feed candidate generation.

Confidence:

- `high` for the seed when it has an anchor and its Trends series shows interest at or above `MIN_TRENDS_INTEREST`.
- `medium` for every candidate with an anchor (Trends is never bought per candidate) and for a seed without Trends signal.
- `low` when there is no anchor; volume is null and the UI shows "< 10".

Version 1 (superseded) scaled the anchor by a "YouTube share" derived from the seed's Trends interest relative to a benchmark keyword sent in the same request, with candidates inheriting a dampened share.
The calibration showed the share model fits neither end of the volume range and that the Trends scaling did not improve rank agreement, so the benchmark request was dropped.

### Channels and breakout

The Channels sub-tab is derived from the ranking videos, so it costs nothing extra: one row per distinct channel with subscribers, views summed over its ranking videos, video count, best rank, and the highest channel multiplier.
A channel is a "breakout" for the keyword when it has at most `BREAKOUT.maxSubscribers` (100K) subscribers and a ranking video has at least `BREAKOUT.channelMultiplier` (10) times the channel's median views, or, without the Data API, `BREAKOUT.viewsPerSubscriber` (3) times the channel's subscriber count.
The first draft (3x, no size cap) flagged all 15 channels for "banana bread"; 10x with a 500K cap flagged 6; the user pointed at VidIQ breakouts with a few thousand subscribers, so the cap is 100K, which flags 3 (44K, 58K, and 63K subscriber channels with 110x to 511x hits).
Formula in `src/shared/youtube-channels.ts`; the service attaches `channels` to every videos result (cached rows only, channels recomputed on read).

### Overall score (0 to 100)

`overall = round(100 * volumeScore^0.5 * (1 - competition / 100)^0.5)` where `volumeScore` is `log10(estimate + 1) / log10(upperBound + 1)` clamped to 0 to 1.
Null when volume is null.

### Word count

Split on whitespace after trimming.

### Candidate generation and classification

Version 2 (2026-09-07). Three sources, each held to a relevance rule after "sarah tang" produced a list of other Sarahs:

- YouTube suggest (seed, question prefix + seed, seed + a to z): a suggestion is kept only when it still contains every seed word (stemmed). YouTube autocompletes a prefix it cannot extend by dropping words ("sarah tang b" becomes "sarah b..."), and those fuzzy completions were the off-topic rows.
- Tags of the videos ranking for the seed (video info `keywords`): kept when at least two ranking videos share the tag, or the tag contains the whole seed; platform tags ("video", "shorts", "viral") and fragments of the seed ("sarah", "tang") are ignored. These are the related rows, ordered by how many ranking videos carry them.
- Google Trends related queries (top, then rising) for the seed: kept when they contain the seed or share a context word, a non-stopword word that recurs across at least two ranking videos' titles and tags and is not itself a seed word. Sharing only a seed word is not enough; on "sarah tang" that rule alone let "sarah pan" and "sarah eggar hgtv" through.

Order before the cap: seed suggestions, tags, Trends, prefix and letter suggestions.
`diagnostics.tagCandidateCount` and `diagnostics.droppedOffTopicCount` report the effect; `CACHE_VERSION` 3 recomputes results cached under the old rules.

Classification (unchanged):

- `matching`: contains every word of the seed.
- `question`: begins with a question word (`how`, `what`, `why`, `when`, `where`, `who`, `which`, `can`, `does`, `is`, `should`) or ends with `?`.
  Question takes precedence over matching.
- `related`: everything else.

Version 1 (superseded) accepted every suggestion and every Trends query, so a name seed collected unrelated people who merely shared a first name.
Because candidates now need the ranking videos' tags, the row chain waits for the seed chain (about 10 s) instead of only Trends (about 7 s); a default run is about 26 s.
